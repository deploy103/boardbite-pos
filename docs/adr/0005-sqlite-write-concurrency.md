# 0005 — SQLite 환경에서의 결제 동시성 제어 방식

- 상태: 채택됨
- 날짜: 2026-09-11
- 관련 문서: `docs/adr/0001-tech-stack.md`, `docs/RESEARCH.md`(Agent E — 동시성 제어), `docs/ARCHITECTURE.md` §8

## 배경

`docs/RESEARCH.md` Agent E는 결제 동시성 제어 전략으로 "`SELECT ... FOR UPDATE` + 조건부 UPDATE"를 제안했다. 이는 **PostgreSQL/MySQL 등 행 단위 잠금을 지원하는 RDBMS**를 전제로 한 표준적인 설계다.

그러나 0001 ADR에서 채택한 SQLite는 `SELECT ... FOR UPDATE` 구문 자체를 지원하지 않는다. SQLite의 동시성 모델은 다음과 같이 근본적으로 다르다.

- 여러 트랜잭션이 동시에 읽을 수 있다(WAL 모드에서 특히).
- 그러나 **쓰기 트랜잭션은 항상 하나만** 진행될 수 있다(전체 DB 파일 단위 잠금).
- Prisma의 SQLite 커넥터가 기본으로 여는 트랜잭션은 지연(DEFERRED) 트랜잭션이라, "먼저 읽고 나중에 쓰기 잠금을 얻는" 구조다. 이 경우 두 트랜잭션이 동시에 "잔액을 읽는" 단계까지는 아무 충돌 없이 통과할 수 있고, 그 다음 쓰기 단계에서 순서가 정해진다. **문제는 두 번째 트랜잭션이 첫 번째 트랜잭션이 커밋되기 이전에 읽은, 이미 낡은(stale) 잔액값을 기준으로 쓰기를 시도할 수 있다는 점**이다 — 이것이 바로 막아야 하는 초과결제 레이스 컨디션이다.

## 결정

**Prisma Client의 SQLite 연결 풀을 물리 커넥션 1개로 고정한다.**

```env
DATABASE_URL="file:./dev.db?connection_limit=1"
```

이 설정은 다음을 보장한다.

- BoardBite POS는 단일 Node.js 프로세스로 배포된다(0001 ADR). 이 프로세스 안의 Prisma Client가 오직 하나의 물리 커넥션만 사용하므로, **애플리케이션이 발행하는 모든 쿼리(트랜잭션 포함)는 그 커넥션을 통해 완전히 직렬화되어 실행된다.**
- 두 개의 결제 생성 요청이 `Promise.all`처럼 "동시에" 들어와도, Prisma는 두 번째 요청의 커넥션 획득 자체를 첫 번째 트랜잭션이 끝날 때까지 대기시킨다. 즉 두 번째 트랜잭션이 시작되는 시점에는 이미 첫 번째 트랜잭션의 쓰기가 커밋되어 있고, 두 번째 트랜잭션은 그 이후의 최신 상태를 읽게 된다.
- 결과적으로 `SELECT ... FOR UPDATE`가 달성하려는 목표(트랜잭션 간 읽기-쓰기 순서 보장)를 애플리케이션 레벨 커넥션 직렬화로 동일하게 달성한다.

**아울러 결제 생성 로직(`server/src/services/payment.ts`)은 다음을 지킨다.**

1. 잔액/이미 결제된 수량 조회와 그 결과를 근거로 한 `Payment`/`PaymentAllocation` insert를 **반드시 하나의 `prisma.$transaction(async (tx) => {...})` 블록 안에서** 수행한다. 트랜잭션 밖에서 미리 읽은 값을 트랜잭션 안의 쓰기 조건으로 사용하지 않는다.
2. 그럼에도 불구하고 방어적으로, 최종 insert 직전에 한 번 더 "이미 결제된 수량/총액이 허용 범위를 넘지 않는지"를 재확인하는 이중 검증을 둔다(코드 리뷰/버그로 인한 회귀에 대비한 안전망).
3. `Payment.idempotencyKey`에 UNIQUE 제약을 걸어 중복 제출 자체를 DB 레벨에서 차단한다(더블클릭/네트워크 재시도 대응, `docs/RESEARCH.md` Agent D 근거는 그대로 유지).

## 트레이드오프로 받아들이는 것

- `connection_limit=1`은 읽기 쿼리도 전부 이 하나의 커넥션을 거치므로, 매우 높은 동시 읽기 부하에서는 처리량이 병목될 수 있다. 그러나 학교 반 부스 규모(동시 사용자 수십 명, 결제 트랜잭션은 그보다 훨씬 적음)에서는 문제가 되지 않는다.
- 다중 서버/다중 프로세스로 수평 확장할 경우 이 방식은 더 이상 유효하지 않다(각 프로세스가 자신만의 커넥션 풀을 가지므로 프로세스 간 직렬화가 깨짐). 그 시점에는 PostgreSQL 등 행 단위 잠금을 지원하는 DB로 전환하고, `docs/RESEARCH.md` Agent E가 원래 제안한 `SELECT ... FOR UPDATE` 방식으로 되돌아가야 한다(새 ADR 필요).

## 적용하지 않는 것

- Redis 등 외부 분산 락 시스템은 도입하지 않는다 — 단일 프로세스 배포 원칙(0001 ADR)과 SQLite 커넥션 직렬화만으로 충분하다.
