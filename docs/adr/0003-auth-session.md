# 0003 — 인증/세션 방식

- 상태: 채택됨
- 날짜: 2026-09-11
- 관련 문서: `docs/SECURITY.md`, `docs/adr/0004-table-token.md`

## 배경

BoardBite POS에는 두 종류의 완전히 다른 "세션"이 존재한다.

1. **직원 세션**: ID/PW로 로그인하는 FRONT/POS/SERVING/ADMIN 계정. 재사용 가능한 로그인이며 역할(role) 기반 권한 검사가 필요하다.
2. **손님(테이블) 세션**: 로그인 없이 QR/NFC로 접근하는 임시 세션. 테이블이 CLOSE되면 즉시 폐기되어야 하고, 순차 추측이 불가능해야 한다(`docs/RESEARCH.md` Agent D 참고).

두 세션은 요구사항과 위협 모델이 다르므로 같은 메커니즘으로 통일하지 않는다.

## 후보 비교 (직원 세션)

- **JWT(무상태)**: 서버가 세션을 저장하지 않아 수평 확장에 유리하지만, "로그인/역할변경 시 즉시 무효화"가 어렵다(블랙리스트 관리가 필요해 사실상 상태를 갖게 됨). 관리자가 계정을 비활성화해도 기존 JWT가 만료 전까지 유효할 위험이 있다.
- **서버 세션(쿠키 + 서버 저장소)**: 로그아웃/역할변경/계정비활성화 시 서버에서 즉시 세션 레코드를 삭제하면 즉시 무효화된다. 단일 프로세스 배포(0001 ADR)이므로 세션을 메모리 또는 SQLite 세션 테이블에 저장해도 별도 인프라(Redis 등)가 필요 없다.

## 결정 (직원 세션)

**서버 세션(쿠키 기반)을 채택**한다.

- 세션 저장소: SQLite 기반 세션 테이블(Prisma로 관리, TTL 만료 처리) — 별도 Redis 불필요(0001 ADR의 단순성 원칙과 일관).
- 쿠키 속성: `HttpOnly; Secure(운영 환경); SameSite=Lax; 만료 8~12시간`.
- 로그인 성공, 비밀번호 변경, 역할 변경 시 세션 ID를 재발급(regenerate)한다(세션 고정 공격 방지, `docs/RESEARCH.md` Agent D 근거).
- 역할(role)은 서버가 매 요청마다 DB에서 재검증하며 클라이언트가 보내는 role 클레임은 신뢰하지 않는다.
- 비밀번호는 bcrypt(또는 argon2)로 해싱하여 저장한다.
- 로그인 실패 5회 시 계정 5분 잠금 + IP 단위 rate limit을 병행한다.

## 후보 비교 (손님 테이블 세션)

- **쿠키 기반 로그인 세션과 동일한 메커니즘 재사용**: 손님은 로그인을 하지 않으므로 "세션"의 발급 트리거가 다르다. 재사용 시 코드는 단순해지지만 "테이블 단위 폐기"와 "직원 인증"이라는 서로 다른 무효화 정책이 한 메커니즘에 뒤섞여 버그 위험이 커진다.
- **테이블 전용 opaque 토큰 + 별도 TableSession 엔티티**: 로그인 없이도 발급 가능하고, 테이블 CLOSE 시 해당 TableSession 레코드만 무효화하면 되어 직원 인증 로직과 완전히 독립적으로 관리된다.

## 결정 (손님 테이블 세션)

**테이블 전용 opaque 토큰 + 별도 `TableSession` 엔티티**를 채택한다. 세부 설계는 `docs/adr/0004-table-token.md` 참고.

## 이유

직원 인증(재사용 가능한 로그인, RBAC)과 손님 접근(1회성, 테이블 수명과 결합)은 무효화 시점과 위협 모델이 근본적으로 다르므로, 하나의 세션 메커니즘으로 억지로 통일하기보다 명확히 분리하는 것이 보안 검증과 유지보수를 쉽게 한다.
