# 0002 — 실시간 통신 방식 선택

- 상태: 채택됨
- 날짜: 2026-09-11
- 관련 문서: `docs/adr/0001-tech-stack.md`, `docs/RESEARCH.md` (Agent B — 네트워크 재연결 섹션)

## 배경

다음 화면들이 서버 상태 변화를 실시간에 가깝게 반영해야 한다.

- 고객 주문 상태(접수/조리중/준비완료/서빙완료)
- POS/KDS 신규 주문 알림
- SERVING의 READY 주문 목록
- FRONT의 테이블 현황/누적 금액

요구사항(`요구사항.md` §18)은 "새로고침을 강요하지 않고, 네트워크가 끊겼다가 복구되면 자동 재동기화"할 것을 명시한다. 행사장(체육관/강당 등)은 상용 매장보다 네트워크가 불안정할 수 있다(`docs/RESEARCH.md` Agent B 참고).

## 후보 비교

### WebSocket (Socket.IO)

- 양방향 실시간 통신, 서버가 상태 변화를 즉시 push 가능.
- Socket.IO는 WebSocket 연결 실패 시 자동으로 HTTP long-polling으로 폴백하고, 재연결 시 자동 재시도(exponential backoff)를 라이브러리 레벨에서 처리한다.
- Room 개념으로 "테이블별 채널", "역할별 채널(KDS/SERVING/FRONT)"을 쉽게 분리할 수 있어 불필요한 브로드캐스트를 줄일 수 있다.
- 단점: 순수 WebSocket 표준보다 프로토콜 오버헤드가 약간 있고, Socket.IO 클라이언트/서버 버전을 맞춰야 함.

### Server-Sent Events(SSE)

- 서버→클라이언트 단방향 스트림. 브라우저 `EventSource`가 자동 재연결을 기본 지원.
- 구현이 WebSocket보다 단순(순수 HTTP 기반)하고 프록시/방화벽 호환성이 좋음.
- 단점: 클라이언트→서버 방향은 별도의 일반 HTTP 요청(REST)으로 처리해야 함(이 프로젝트는 어차피 주문/결제를 REST POST로 처리하므로 큰 단점은 아님). 다만 오래된 iOS Safari 일부 버전에서 백그라운드 탭 처리 이슈가 보고된 사례가 있고, 다중 탭에서 연결 수 제한(브라우저당 HTTP/1.1 기준 6개)에 걸릴 수 있음(HTTP/2 사용 시 완화).

### Short Polling

- 클라이언트가 일정 주기(예: 3~5초)로 REST API를 호출해 상태를 조회.
- 구현이 가장 단순하고 인프라 요구사항이 없음(방화벽/프록시 이슈 없음).
- 단점: 실시간성이 폴링 주기에 종속되고, 다수 클라이언트가 동시에 폴링하면 서버 부하가 리니어하게 증가. "즉시 알림"이 중요한 KDS 신규 주문 알림에는 지연이 체감될 수 있음.

## 결정

**Socket.IO(WebSocket 우선, long-polling 자동 폴백)를 1차 실시간 채널로 채택**하고, **Socket.IO 연결 자체가 완전히 불가능한 극단적 네트워크 환경을 대비해 각 화면에 낮은 빈도(예: 15~30초)의 REST 폴링 안전망을 이중으로 둔다.**

역할/테이블 단위로 Socket.IO room을 분리한다.

```text
room: table:{tableSessionId}   -- 해당 테이블 손님 화면
room: staff:pos                -- POS/KDS 화면
room: staff:serving            -- SERVING 화면
room: staff:front              -- FRONT 화면
room: staff:admin              -- ADMIN 대시보드
```

서버는 상태가 바뀌는 시점(주문 생성/상태 변경/결제/테이블 OPEN·CLOSE)에 해당 room에만 이벤트를 emit하고, 클라이언트는 이벤트 수신 시 관련 데이터를 다시 fetch하거나 이벤트 payload로 로컬 상태를 갱신한다. 재연결 시에는 항상 REST API로 "현재 전체 상태"를 다시 가져와 소켓 이벤트 유실을 보정한다(이벤트는 트리거일 뿐 단일 진실 공급원이 아님 — 서버 DB가 단일 진실 공급원).

## 이유

1. KDS 신규 주문 알림과 같이 "즉시성"이 중요한 화면에는 push 기반 WebSocket이 폴링보다 명확히 우월하다.
2. Socket.IO는 재연결/폴백을 자체 처리해 "네트워크 재연결 자동 동기화" 요구사항 구현 비용을 낮춘다.
3. 그럼에도 소켓 이벤트를 "단일 진실 공급원"으로 삼지 않고, 재연결 시 REST로 전체 상태를 재조회하도록 설계해 이벤트 유실에 대한 방어선을 이중화한다 — 학교 행사장의 불안정한 네트워크를 고려한 방어적 설계.
4. 순수 SSE나 짧은 폴링만으로는 KDS의 "새 주문 즉시 알림+알림음" 요구사항을 매끄럽게 satisfy하기 어렵다.

## 적용하지 않는 것

- 별도의 메시지 브로커(Redis Pub/Sub, RabbitMQ 등)는 도입하지 않는다. 단일 Node 프로세스 내에서 Socket.IO 서버가 직접 emit하는 구조로 충분하다(0001 ADR의 단일 프로세스 배포 결정과 일관).
- 다중 서버로 수평 확장할 경우에는 Socket.IO의 Redis adapter 도입이 필요하나, 이는 현재 규모에서 불필요한 선제적 확장이므로 채택하지 않는다.
